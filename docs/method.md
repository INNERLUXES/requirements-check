# Method

The tool answers one question: do these dependency files install only what the team expects, from where the team expects it, in a way pip or the locker can verify, and the same way on every build? It reads the requirements files and lock files it is given, turns every requirement and locked package into a record of its name, version or specifier, source, hashes, file and line, and runs the checks below on those records. It never runs pip or Python and never asks an index anything.

The formats it reads are described in pip's documentation, [Requirements File Format](https://pip.pypa.io/en/stable/reference/requirements-file-format/), and in the lock file formats of uv and Poetry. Names, versions, specifiers and markers follow the Python packaging standards: [PEP 503](https://peps.python.org/pep-0503/) for name normalisation, [PEP 440](https://peps.python.org/pep-0440/) for versions and version specifiers, and [PEP 508](https://peps.python.org/pep-0508/) for the form of a requirement, its extras, its direct references and its environment markers.

## Why the dependency files are worth a gate

A Python web application imports every package it installs into the same process as its own code: the same environment variables, the same database connection, the same secret key and the same access to the data of its users. A package that runs code at import time runs it in production. The requirements files and the lock file are the only place that says which packages these are, at which version, from which index, and with which hashes. `pip install -r requirements.txt` installs what the file allows on the day it runs; a lock file, installed with `uv sync --frozen` or `poetry install`, installs exactly what was locked.

pip's documentation on [Secure installs](https://pip.pypa.io/en/stable/topics/secure-installs/) describes what makes an installation repeatable and safe: pin every requirement to an exact version, record the hash of every file (`--hash`, with `--require-hashes` to make pip refuse anything without one), and treat each index as a source of code that can run on the build machine. NIST SP 800-218, the [Secure Software Development Framework](https://csrc.nist.gov/pubs/sp/800/218/final), asks for the same in its practices on protecting all forms of code from tampering (PS.1), verifying the integrity of third-party components and reusing well-secured software (PW.4), and keeping the build environment under control (PO.5). A check of the dependency files is a small, cheap piece of both: it runs on every pull request, needs no network, and turns a change to a requirements file into a short list of facts a reviewer can judge.

A finding is an **error** when the build would install something it cannot verify, from a place outside the team's control, or something other than what was reviewed: a direct reference, an unencrypted download, a requirement without a pin, a missing hash in hash-checking mode, two different pins for one package, a constraint that cannot hold, a lock file out of step. It is a **warning** when something should be looked at but may be intended: an extra index, a trusted host, an unpinned development tool, a weak hash. It is **info** when nothing is wrong but the fact is useful.

## How requirements files are read

The tool reads a requirements file in the order pip does:

1. **Lines.** A line that ends with a backslash is joined with the next one. Then comments are removed: a `#` at the start of a line or after white space starts a comment, so the `#sha256=` fragment of a URL is kept. Every logical line keeps the number of its first physical line, which the report shows.
2. **Options lines.** A line that starts with `-` is an option: `-r` / `--requirement` and `-c` / `--constraint` (includes), `-i` / `--index-url`, `--extra-index-url`, `-f` / `--find-links`, `--trusted-host`, `--require-hashes`, `--no-index`, `--pre`, `--prefer-binary`, `--only-binary`, `--no-binary`, `--use-feature`, and `-e` / `--editable`. Each is read in every spelling pip accepts (`-r file`, `-rfile`, `--requirement file`, `--requirement=file`). An option the tool does not know is listed in a note, not guessed at.
3. **Requirements.** Any other line is a requirement followed by its own options. As in pip, the options start at the first word that starts with `-`; `--hash=algorithm:digest` (or `--hash algorithm:digest`) may appear several times. A hash that is not `algorithm:hex-digest` with a known algorithm stops the run.
4. **The requirement itself** follows PEP 508: a name, optional extras in brackets, an optional specifier list (with or without parentheses), and an optional environment marker after `;`. A direct reference is written `name @ url`, or as a URL or path on its own, named by its `#egg=` fragment, its archive file name or its folder. After a URL, a marker needs white space before the `;`, since a URL may hold one. A line that cannot be read this way stops the run with its file and line: pip would refuse it too, and a check that skipped it would pass a file that does not install.
5. **Includes.** `-r` and `-c` paths are resolved relative to the file that names them. Every included file must lie in the folder of the file named on the command line, or below it, both as written and after symbolic links are followed; anything else is refused. An include that names a URL is recorded and reported, never fetched. A file included twice is read once; a file that includes itself, directly or through others, stops the run with the chain of files. Requirements read through `-c` are constraints: they limit versions but install nothing.

**Names** are compared in their PEP 503 form: lower case, with every run of `-`, `_` and `.` read as one `-`. `Example_Web.Framework` and `example-web-framework` are the same package.

**Versions and specifiers** follow PEP 440: epochs, release numbers, prereleases (`a`, `b`, `rc` and their long spellings), post and dev releases, and local versions, with their normalisation and their order. The specifier operators `==` (with a `.*` prefix wildcard), `!=`, `~=`, `<`, `<=`, `>`, `>=` and `===` are read; trailing zeros do not matter (`1.0` is `1.0.0`), `>1.7` does not match a post release of 1.7, and `<1.7` does not match a prerelease of it. The rule that leaves prereleases out unless a specifier names one is not applied when comparing a pinned or locked version, since that version was chosen on purpose. A version that is not PEP 440 is compared only with `===`, and otherwise reported in a note rather than counted as a match or a mismatch.

**A pin** is a specifier list with an `==` clause without a wildcard, or an `===` clause. `==1.4.*`, `~=1.4` and `>=1.4,<2` are not pins: each allows more than one version.

**Hash-checking mode** is on for a requirements file, and every file it includes, when any of them has `--require-hashes` or any requirement has a `--hash` option, as pip does. A `#sha256=` fragment on a URL is checked by pip as a hash, but does not turn the mode on.

**Development files** are named by pattern. By default these are `requirements-dev*`, `requirements_dev*`, `dev-requirements*`, `requirements-test*`, `requirements_test*`, `test-requirements*`, `*-dev.txt` and `*.in` (the input files of pip-compile); the config can replace the list and `--dev-pattern` can add to it. The pattern is matched against the file name only, for each included file on its own.

## How lock files are read

`uv.lock` and `poetry.lock` are TOML files. The tool reads them with a small TOML reader of its own that covers what these files use: key/value pairs with bare, quoted and dotted keys, `[tables]` and `[[arrays of tables]]`, basic and literal strings on one line or several, decimal integers and floats, `true` and `false`, arrays over several lines, and inline tables on one line. Dates and times, hexadecimal, octal and binary numbers, `inf` and `nan`, an inline table over several lines, a key defined twice or a table defined twice stop the run with the line where they appear. The reader never guesses.

- **uv.lock**: each `[[package]]` has a `name`, a `version` and a `source`: `registry` (an index URL), `git`, `url`, `path`, `directory`, `editable` or `virtual`. A `virtual` or `editable` source of `.` is the project itself and is not a dependency. Hashes come from `sdist` and `wheels`.
- **poetry.lock**: each `[[package]]` has a `name`, a `version` and `files` with their hashes. Without a `[package.source]` it came from PyPI; a source of type `legacy` is another index, and `git`, `url`, `file` and `directory` are direct references (`develop = true` marks an editable folder). Older files keep the hashes in `[metadata.files]`, by name; the tool reads them there.

A file named `uv.lock` or `poetry.lock` is read as that format; any other `.lock` file is recognised by its contents, and refused when it is neither.

## The checks

| Id | Severity | Rule and why it matters |
| --- | --- | --- |
| `non-index-source` | error | The package comes from a direct reference: a git (or Mercurial, Subversion, Bazaar) URL, an archive URL, a local path, an editable install (`-e`), or the source of a locked package is one of these. An index keeps a released file immutable and serves it with a hash; a branch or tag can be moved, a URL can serve another file tomorrow, a local folder holds whatever is on the build machine, and an editable install runs that folder's build. A requirements file included by URL is reported here too: pip downloads it at install time, and nobody reviewed what it says that day. References that start with a prefix in `allowDirect` are accepted |
| `insecure-url` | error / warning | An index, extra index, find-links location, direct reference or included file is fetched over `http://`, `ftp://`, `git://`, `svn://` or a VCS `+http` form: anyone on the network path can change what is downloaded. pip's secure installs guide asks for https. `--trusted-host` is a warning: it tells pip to accept that host without a valid certificate, or over plain http |
| `unpinned` | error / warning | A requirement has no exact pin. pip then installs the newest matching version on the day of the build, so two builds of the same commit can install different code, and a release published an hour ago reaches production without review. pip's secure installs guide asks for every requirement to be pinned. In a development file the finding is a warning: those tools do not reach production, though they do run on developer machines and in CI |
| `missing-hash` | error / warning | In hash-checking mode a requirement without a hash makes pip refuse the whole install; reporting it here says which line to fix. In a lock file that records hashes for its other packages, a package from an index or URL without one cannot be checked. With `--want-hashes`, requirements without hashes are warnings in any file: a hash is what proves the downloaded file is the one that was reviewed |
| `duplicate-requirement` | error | The same package (by its PEP 503 name) is listed twice with different pins or references, in the file or in the files it includes. Depending on its version, pip refuses the pair or installs one of them; either way, the file says two things. Requirements with different environment markers are for different systems and are not compared |
| `conflicting-constraint` | error | A requirement's pin is outside a `-c` constraint for the same package, or a constraint's pin is outside the requirement's specifier. pip cannot satisfy both and the install fails, often only on the build server |
| `lock-mismatch` | error | With `--requirements` and `--lock`: a requirement of the requirements file (and the files it includes) is not in the lock file, or its locked version does not satisfy the requirement's specifier. The build then installs something the lock file never saw, or the lock file holds a version the requirements no longer allow. A requirement with an environment marker that is missing from the lock file is not reported, since it may belong to another system |
| `extra-index` | warning / error | `--extra-index-url` adds a second index. pip looks in every index and takes the highest version it finds, so anyone who publishes a private package name on the public index with a higher version replaces the private package: dependency confusion. The tool keeps the rule simple: every extra index is a warning; a package named in `privatePackages` that has no hash in a file with an extra index is an error (a hash would tie it to one file, whichever index serves it); in a lock file, a package named in `privatePackages` that was locked from `https://pypi.org/simple` is an error, and a lock file with packages from more than one index is a warning |
| `weak-hash` | warning | A hash is made with MD5 or SHA-1, for which collisions can be produced. pip refuses these algorithms in `--hash`; they still turn up in URL fragments and old lock files |
| `marker-note` | info | A requirement has an environment marker (`; sys_platform == "win32"`, `; python_version < "3.13"`), so it is installed only on some systems or Python versions. Listed so a reviewer sees which packages production may or may not get |

## Config, ignore rules and the gate

The config file sets the accepted direct reference prefixes, the names of private packages, the development file patterns and ignore rules. An ignore rule leaves a finding out of the report and the gate; the report says how many were left out, so an ignore rule is never invisible.

`--fail-on error`, the default, makes the run exit with `1` when any error is found. `--fail-on warning` also fails on warnings. Info never fails a run. The gate counts every finding, also those beyond `--limit`, which only shortens the lists that are shown.

## The report

Each report shows the inputs, the number of requirements, constraints and lock files read, a summary of the packages (pinned, with hashes, direct references) and the indexes, a table of every requirement and locked package with its version, source, hashes and location, the findings ordered by severity, check, file and line, the notes, and the gate. Every text taken from the input has credentials in URLs replaced by `***` and control characters removed before it reaches any format.

The method has no randomness and no network access: the same files always give the same report, and any change in the report comes from a change in the files.
